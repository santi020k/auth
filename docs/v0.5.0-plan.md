# v0.5.0 release plan

Status: planned on `release/v0.5.0` from merged `main` commit `5e4eaba`.

Version 0.5.0 should turn the machine-credential primitives introduced in v0.4.0 into a complete, reusable HTTP
integration without expanding Auth into a shared identity service. The release remains additive: consumers continue to
own credentials, persistence, routes, scopes, audit storage, and rollout authorization.

The v0.4.0 registry bootstrap and trusted-publisher setup are operational prerequisites for publishing v0.5.0. This
plan does not authorize npm publication, tags, GitHub Releases, deployments, secrets, or consumer migrations.

## Release outcomes

### 1. Asynchronous machine credential resolution

Add a bounded asynchronous resolver contract to `@santi020k/auth-machine` so a Worker can look up one credential by the
identifier embedded in the bearer token instead of loading and scanning a complete environment JSON array.

Acceptance criteria:

- The bearer header and encoded token have explicit maximum lengths, and the existing 80-character credential
  identifier limit is enforced before invoking the resolver or emitting an event.
- The resolver receives only the validated credential identifier and returns one digest record or `null`.
- Existing array-based `resolveMachineBearer` usage remains supported.
- Unknown, expired, not-yet-active, revoked, malformed, and digest-mismatched credentials fail closed with redacted
  events.
- Oversized or malformed attacker-controlled input never reaches the resolver and produces only a stable redacted
  reason in events, without echoing any part of the credential.
- Resolver failures return a safe authentication failure while preserving useful consumer-owned diagnostic context.
- Record, scope, identifier, and timestamp bounds remain enforced at the storage boundary.

### 2. Scope-enforcing Hono middleware

Add `createRequireHonoMachineAuth` to `@santi020k/auth-hono`, integrating the machine resolver without mixing machine
principals with browser sessions.

Acceptance criteria:

- Every protected route declares at least one required scope; an empty scope list is rejected during middleware setup.
- The authenticated machine principal is exposed through a typed consumer callback rather than a global identity store.
- Package-owned failures return `401` for missing or invalid credentials and `403` for insufficient scopes, always set
  `Cache-Control: no-store`, and never reveal token, digest, or credential inventory details.
- Consumers may customize only the response body through a constrained mapper that receives a redacted reason and,
  for insufficient scope, the authenticated principal. The package retains ownership of status and security headers,
  and the mapper never receives the raw authorization header, token, or digest record.
- Hono depends on `@santi020k/auth-machine` through `workspace:*`, and package ordering remains release-validator driven.

### 3. Explicit credential lifecycle helpers

Add lifecycle helpers for revocation, replacement, and safe inventory so consumers can build operator tooling without
reimplementing timestamp and redaction rules.

Acceptance criteria:

- Revocation is idempotent and never removes the audit-relevant record implicitly.
- Rotation creates a new one-time plaintext token and a new digest record; it never returns or reconstructs an existing
  secret.
- Rotation uses `crypto.getRandomValues` by default. Tests may inject an explicit entropy source, but production
  examples and defaults never use deterministic entropy.
- A consumer chooses any overlap window explicitly. The library does not silently keep an old credential active.
- Inventory exposes safe metadata only: identifier, display name, subject, scopes, and lifecycle timestamps.
- Lifecycle decisions are deterministic under an injected clock, while secret generation remains cryptographically
  random; every helper has boundary tests.

### 4. Reusable machine-auth contract tests

Extend `@santi020k/auth-testing` with requests and assertions for machine-authenticated Hono routes.

Acceptance criteria:

- Fixtures cover valid credentials, missing bearer headers, malformed and oversized headers or tokens, unknown
  identifiers, overlong identifiers, digest mismatch, activation boundaries, expiry, revocation, and insufficient
  scopes.
- Tests prove that raw tokens and token hashes never appear in events or HTTP responses.
- A packed external consumer type-checks the new public exports without monorepo-only resolution.
- Node 22.22.3 and Node 24 compatibility jobs remain green.

### 5. Runnable example and package documentation

Add one local-only playground route that demonstrates a scoped machine client separately from browser login, and extend
the package guide with storage, middleware, rotation, and incident-response examples.

Acceptance criteria:

- The example uses a development-only credential and cannot expose its token outside localhost.
- Browser sessions cannot satisfy the machine route, and machine credentials cannot satisfy browser-session routes.
- Documentation shows Infisical or another consumer secret manager as the raw-token delivery boundary without logging
  or committing the token.
- Desktop and mobile documentation checks retain level AA accessibility behavior and no horizontal overflow.

## Delivery sequence

1. Resolve the v0.4.0 one-time npm bootstrap and configure trusted publishing for all seven new split packages.
2. Add the async resolver contract and focused security tests in `auth-machine`.
3. Add the Hono middleware and its typed integration tests.
4. Add lifecycle helpers and machine fixtures after the core resolver API is stable.
5. Add the playground and Lumen documentation after public API names settle.
6. Add Changesets, migration notes, and a rollback or forward-recovery plan; run `pnpm verify` and `pnpm release:pack`.
7. Obtain an independent full-diff review before the first push of release-ready implementation changes.

## Explicit non-goals

- No shared credential database, cross-product secret, session, cookie, passkey, relying-party ID, or recovery policy.
- No implicit D1 schema creation or production data mutation.
- No product roles, invitations, organizations, or impersonation policy.
- No native mobile or desktop OAuth, PKCE, token exchange, or device-bound session work in v0.5.0; that requires a
  separate architecture decision and consumer demand.
- No generic “human or machine” middleware that could blur authorization boundaries.
- No npm publication, deployment, or consumer cutover as a side effect of implementing the plan.

## Release evidence

The release candidate is ready for its pull request only when:

- all public contracts and errors are documented with migration notes;
- unit, integration, packed-consumer, rendered playground, accessibility, and supported-runtime tests pass;
- machine secrets stay absent from logs, fixtures, screenshots, events, and committed files;
- the fixed package group is versioned together at `0.5.0` through Changesets;
- the complete release diff receives an independent pre-push review; and
- `pnpm verify`, `pnpm release:pack`, `quality doctor --format pretty`, and `quality hooks status` pass on the exact
  candidate commit.
